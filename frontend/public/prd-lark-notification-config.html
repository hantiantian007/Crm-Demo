4. 三个场景的完整业务逻辑

下方三个「消息模板」用于国际版 Lark 群消息通知。保留 {{字段名称}} 动态变量占位符，每行一个字段，正式生成消息时按业务数据填充；消息展示字段严格以各场景模板为准，不添加「查看详情」链接或「触发条件」字段。前文业务事件字段用于计算、去重及记录，不要求全部出现在群消息正文中。原有触发条件、计算规则、去重规则及通知群组配置保持不变。

暂缓规则存档：活动有人疑似对冲交易（当前隐藏）

活动有人疑似对冲交易 · 非本期

触发：活动相关订单平仓后，业务模块完成订单匹配，首次确认满足疑似对冲条件时生成事件并通知。

范围与来源：仅已平仓、与同一活动相关且符合其交易统计范围的订单；按MT交易服务器时间计算，不用客户端本地时间。仅不同交易账户之间配对：同客户不同账户可匹配；跨客户账户须符合系统既有账户关联识别规则。不同活动不能合并组数，通知模块不新增账户关联算法。

必须同时满足的判断项规则
交易账户 / 品种 / 方向不同交易账户；MT交易服务器的标准品种代码相同；一买一卖。
开仓时间差ABS(A开仓时间－B开仓时间) ≤ 5分钟（300秒）。
有效平仓手数差异率ABS(A有效平仓手数－B有效平仓手数) / MAX(A有效平仓手数, B有效平仓手数) × 100% ≤ 10%。
持仓时长每笔持仓时长＝平仓时间－开仓时间。
持仓时长差异率ABS(A持仓时长－B持仓时长) / MAX(A持仓时长, B持仓时长) × 100% ≤ 10%。
组数同一活动、同一关联账户范围内，滚动24小时至少2组有效匹配。
  • 配对：先筛选满足全部配对条件的候选订单对，按开仓时间差从小到大选择；差相同时按订单编号升序确定配对。每对订单编号先按来源系统的既有编号排序口径规范化，再按两编号顺序比较，保证A-B与B-A只算一组。
  • 同一活动、同一检测批次内，每笔订单最多参与一组有效匹配。部分平仓按既有MT订单/成交口径统计，不把同一订单的多个成交拆成重复匹配；不同检测批次重算同一订单对不重复累计组数。
  • 第一组只记录不通知；滚动窗口首次达到第二组时触发。两项差异率都必须≤10%；不能用“平仓时间差≤10分钟”替代本期持仓时长差异率。
  • 排除及边界：必要字段缺失、任一有效平仓手数为0、两笔持仓时长都为0时不匹配，避免除零。一笔时长为0、另一笔为正时差异率100%，不通过。异常时间或无效交易数据交由业务模块按既有数据质量规则处理，不据此推定命中。
  • 去重：同一活动＋同一关联账户组合＋同一对冲事件，只发送一次首次命中通知；后续增加匹配订单只更新事件详情。新的独立事件可重新通知；已处理事件发生新的独立对冲行为允许生成新事件。不能仅因重复扫描、批次变化或重试生成新事件。
  • 通知内容：活动名称及编号、客户ID（涉及多客户时全部列出）、涉及账户、关联订单、交易品种、方向、手数、开仓/平仓时间、持仓时长、匹配组数、命中规则、触发时间、CRM详情链接。
  • 只提示“疑似对冲”，不直接认定违规，不修改活动手数、奖励或交易统计。

正式检测需沿用已有对冲事件边界和滚动窗口口径；若现有系统未定义，实施前由产品确认“匹配组归属窗口的时间锚点及边界、独立事件划分及关闭条件、同一组合的范围标识”。本文不擅自新增固定冷却期，也不将每天或每批次视为新事件。本期仅文档和展示，不实现这些检测。

场景验收：①开仓差恰为300秒、两差异率恰为10%均通过对应判断，超过即失败；②仅1组不通知，首次2组通知，A-B/B-A及共用订单不能凑组；③跨活动、无关联跨客户、缺字段、零手数或双方零时长不匹配；④同事件增单不重发，新独立事件可发；⑤通知不改变业务统计或奖励。

4.1 活动有人参与

触发与来源：活动业务模块完成资格校验并成功保存有效参与记录后立即触发。需报名活动以报名成功为准；无需报名活动以首次满足活动配置的参与条件为准。依据活动配置、资格校验结果及已保存参与记录，不凭页面操作猜测。

  • 浏览活动页、点击入口、报名失败、不符合资格均不算参与；参与记录保存失败或事务回滚不得通知。
  • 去重键：活动ID + 客户ID（参与通知类型内）。重复点击、请求、接口重试不重发；同客户不同活动分别通知。
  • 退出后重新报名默认不重发；只有产品后续将重报名明确为新参与周期才调整。第一次失败、以后首次成功仍触发。
  • 通知内容：严格使用本场景下方「消息模板」，不追加其他字段。

场景验收：①资格通过且保存成功才通知；②浏览、失败、回滚不通知；③同活动同客户重复请求或退出重报不重发；④不同活动分别发，先失败后首次成功正常发。

4.2 活动有人达标

触发与来源：活动进度更新后，已有效参与的客户首次达到活动配置的最终达标条件时，业务模块立即确认事件并发送通知。来源为参与记录、活动最终条件、符合活动规则的有效交易或任务数据。

  • 目标和判断关系必须读取活动配置；有效平仓手数、有效交易笔数或其他任务指标依原活动计算，不在通知模块重定阈值。被活动规则排除的订单不计入。
  • 示例（非新增通用门槛）：活动目标100 Lot，98 → 100 Lot首次通知，随后120 Lot不重复；未有效参与不能达标通知。多指标的AND/OR及最终达标判断沿用活动配置。
  • 去重：同一活动、同一客户的最终达标事件只通知一次，重复计算/请求不重复。存在多个条件不自动拆分通知；只有已被定义为独立通知事件的条件，才按独立事件标识分别去重。
  • 通知内容：严格使用本场景下方「消息模板」，不追加其他字段。
  • 奖励自动发放或人工审核均沿用原活动规则；通知不直接修改奖励状态。缺失最终条件或有效数据无法确认时不伪造达标，业务确认后再处理。

场景验收：①有效参与并首次满足配置的最终条件才触发；②98→100发、100→120及重复计算不重发；③被排除订单不计入；④多个指标不擅自拆为多个通知，独立事件按配置分别去重；⑤奖励状态不被通知改变。

4.3 大额出金

触发：客户成功提交出金，生成有效出金申请编号后立即判断。创建失败或没有有效编号不通知。金额不以审核通过或实际到账为触发时点。

条件A：本次出金金额（USD） ≥ 5,000。

条件B：过去24小时有效入金总额（USD） > 0，且 本次出金金额（USD） / 过去24小时有效入金总额（USD） ≥ 50%。

最终判断：A OR B；两者同时满足也仅通知一次，命中条件记录“两者同时命中”。

  • 统计窗口与来源：以出金申请创建时间向前滚动24小时，按入金成功入账时间筛选有效入金记录。窗口端点包含口径沿用现有资金统计规范；若未定义，正式开发前确认，不混用申请时间、客户端时间。
  • 仅统计该客户、该交易账户的有效入金；不同账户不直接合并。只有既有资金业务明确以客户钱包为统一核算主体时才按该钱包口径计算，不临时扩大到所有账户。
  • 失败、撤销入金排除；退款/冲正按财务确认的有效入金口径扣除。出金/入金统一换算USD，沿用公司现有汇率及时间口径，保留原币种与金额。
  • 入金总额为0时B不成立；非正总额也不满足“>0”，不得除零。A仍独立判断；金额或汇率数据缺失不当作0，交业务模块核对，不捏造命中结果。
  • 去重键：出金申请ID + 通知类型（大额出金）。重复请求/计算只处理同一首次通知；同客户不同申请分别判断。
  • 修改申请金额默认不重发首次通知；修改后首次达到门槛是否补充提醒，待产品另行确认，本期不增加补充事件。取消后重提并生成新编号，视为新申请重新计算。
  • 通知内容：严格使用本场景下方「消息模板」，不追加其他字段。
  • 大额出金只是提醒，不等同高风险判定，不自动拒绝，不改变审核流程。

5. 统一通知机制（正式开发约定）

  1. 业务模块计算并确认有效事件；Lark通知模块只接收事件、匹配已配置启用群组、生成群消息和发送。通知模块不重新计算活动进度、账户关联或出金门槛。
  2. 同一业务事件、同一通知类型不得因请求/重试重复创建通知；同时满足各场景业务去重键，不能通过重建事件ID绕过去重。
  3. 一个事件可以有多个接收群组，每群分别保存投递结果；同一任务、同一群目标不得重复新建。群A成功、群B失败必须分别可追溯，不能将整体标成全部成功。
  4. 失败记录状态和原因；后续重试复用原通知任务及对应群投递，不新建业务通知，不对已成功群重复首次投递。重试触发方式/次数不在本期扩展，也不承诺网络层严格只送达一次。
  5. Lark发送失败不得回滚有效参与、达标结果、对冲事件或出金申请；发送失败与业务失败分开。
  6. 至少保存事件类型、业务事件编号、接收群组、内容、触发时间、发送时间、发送状态、失败原因；原事件内容与目标群名称作为快照，不因后续编辑改写历史。不记录Webhook凭证。
  7. 规则停用或没有启用群组时不发送，不回退到个人单聊。配置与群管理仍采用现有可保存空群组规则；恢复配置后的历史补发不属于本期。
  8. 通知不能改变活动状态、奖励状态、交易统计或出金审核状态。只有国际版Lark群消息方案，不维护个人ID，不调用国内飞书接口。

本次前端保留既有手动模拟能力和历史演示记录，不新增逐群投递数据结构、事件触发器或自动重试。模拟记录仍明确标注演示，不能作为以上正式机制已经实现的依据。正式Webhook及敏感信息由后端安全保存，不能写死在前端。

6. 操作、状态及异常

  • 设置：回填本规则群组及开关；多选一个或多个已启用群组，保存后列表同步。名称/说明只读，取消不改配置。空群组可保存但提示不发送。
  • 保存时核对群组仍存在且启用；失效群不可选。群停用/删除联动移除引用，重新启用不自动勾选；改名不改历史。
  • 规则状态仅“启用 / 停用”；群状态沿用群组管理。配置启用不等同消息发送成功。存储失败提示仅本次会话生效，不冒充持久化成功。
  • 手动模拟选项与当前三场景一致；停用规则不可模拟，历史旧场景记录照常查看，不因此恢复旧配置项。
  • 正式业务字段不足、时间口径不明确或独立事件边界未定义时由业务模块核对，不能由通知模块填造数据或默认为已命中。权限仍沿用既有CRM规则。

7. 验收标准

本期原型验收

  1. 通知配置恰好3条，名称/顺序/说明与第2节一致，无其他场景；原有三个Tab、默认通知记录及PRD入口不变。
  2. 每条规则支持多选启用群组、启停、保存、取消及刷新回填；三个活动规则原配置保留，大额出金不误用旧高风险配置。
  3. 群组与历史通知未被删除或改写；原有CRM登录通知和其他业务页面不改，不恢复个人单聊。
  4. 没有真实自动检测、网络发送、后台任务或新通知场景；构建通过。

后续正式开发验收

  1. 逐项通过第4节三个生效场景的触发、公式、边界和业务去重测试，所有时间与金额采用指定来源口径。

  3. 多群分别记录成功/失败；重试复用原任务，不重复发送已成功群；触发时间与发送时间分别记录。
  4. 三个场景的群消息按各自模板逐行展示，动态变量对应业务数据，不追加「查看详情」链接、「触发条件」或其他字段；发送失败不回滚业务，不修改奖励、交易或审核状态。
